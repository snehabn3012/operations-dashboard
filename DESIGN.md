# Design Document — Operations Dashboard

This document explains the architecture and the reasoning behind it. The brief's own framing (section 28, "Most Important Architectural Principle") is the design's north star:

> The dashboard must be configuration-driven. Data, presentation, layout, permissions, client state, server state, and module loading should be separate concerns. The dashboard component itself should not need to be modified when a widget is hidden/shown, a widget's type changes, a role is added, a module is added, the layout changes, more modules load through pagination, or the backend replaces the mock API.

Everything below either implements that principle directly or explains where the prototype deliberately cut scope to stay a prototype.

## 1. Architecture overview

```text
Mock API (data/mockApi.ts)
     ↓
RTK Query (store/api/dashboardApi.ts)
     ↓
Server/Data State
     ↓
Dashboard Configuration (config/dashboardConfig.ts, lib/configValidator.ts)
     ↓
Permissions (role → module ids, expressed as data, not code)
     ↓
Widget Renderer (components/dashboard/WidgetRenderer.tsx)
     ↓
Widget Presentation (config/widgetRegistry.ts)
     ↓
Layout (lib/layoutBuckets.ts + DashboardGrid.module.css)
```

Client state (Redux Toolkit, `store/dashboardSlice.ts`): selected role, draft configuration, unsaved-changes flag.
Server state (RTK Query, `store/api/dashboardApi.ts`): the five data sources, dashboard configuration, paginated modules — fetching, caching, loading/error, mutation, invalidation.

## 2. How each "must not change" guarantee is satisfied

| Change | Mechanism | Where |
|---|---|---|
| Widget hidden/shown | `visible` is a field on `WidgetConfig`; `getDashboardModules` filters on it server-side and the renderer never branches on it | `data/mockApi.ts`, `types/dashboard.ts` |
| Widget type changes (Bar Chart → KPI) | `widgetRegistry` is a `WidgetType → component` lookup; `WidgetRenderer` resolves it by key, no `if`/`switch` | `config/widgetRegistry.ts`, `components/dashboard/WidgetRenderer.tsx` |
| A new role is added | Role → module-id list is a data map (`ROLE_MODULE_IDS`); `Dashboard.tsx` only reads `selectedRole` from Redux and never branches on which role it is. Per-role customization (a self-scoped role's relabeled titles and "self" filter) is also data — `ROLE_SELF_SCOPED_FILTER`/`ROLE_WIDGET_TITLE_OVERRIDES`, keyed by role, not an `if (role === ...)` branch | `config/dashboardConfig.ts`, `components/dashboard/Dashboard.tsx` |
| A new module is added | Add an entry to `MODULE_CATALOG` (and optionally `WIDGET_PALETTE`); nothing in the renderer or dashboard shell changes | `config/dashboardConfig.ts`, `config/widgetPalette.ts` |
| Dashboard layout changes | Each widget carries its own `layout: {width, height}`; `lib/layoutBuckets.ts` snaps it into the grid's supported buckets; one shared `DashboardGrid.module.css` is used by both `/dashboard` and the `/configure` canvas | `lib/layoutBuckets.ts`, `components/dashboard/DashboardGrid.module.css` |
| More modules load via pagination | `useInfiniteModules` owns the page cursor; RTK Query's custom `serializeQueryArgs`/`merge` accumulate pages into one cache entry per role, so `ModuleLoader` just renders whatever list it's handed | `hooks/useInfiniteModules.ts`, `store/api/dashboardApi.ts` |
| Backend replaces the mock API | Every mock function is wrapped by exactly one RTK Query `queryFn` in `dashboardApi.ts`; swapping `fakeBaseQuery` for `fetchBaseQuery` and pointing each `queryFn` at a real endpoint is the only change needed — no consumer of these hooks changes | `store/api/dashboardApi.ts`, `data/mockApi.ts` |
| Config is missing/invalid/malformed/from an old version | `validateDashboardConfig` normalizes any payload before it reaches a component, falling back to role defaults instead of throwing; an unresolvable `widgetType` renders `UnsupportedWidget` instead of crashing | `lib/configValidator.ts`, `components/widgets/UnsupportedWidget.tsx` |

## 3. State management split

- **RTK Query** owns everything that is, conceptually, server data: customers/transactions/revenue/orders/payments, dashboard configuration (`getDashboardConfig`/`updateDashboardConfig`), and paginated modules. It's used even against the mock API (via `fakeBaseQuery`), specifically so caching/loading/error/invalidation behave the same way they would against a real backend — see the "backend replaces the mock API" row above.
- **Redux Toolkit** (`dashboardSlice.ts`) owns only client/UI state: `selectedRole`, `draftConfig` (widgets *and* dashboard-level filters — section 14), `isDirty`, and the local undo/redo history (`past`/`future`, see section 10). The draft *is* the live preview — the `/configure` canvas renders directly from `draftConfig`, so there's no second copy of "what the preview shows" to keep in sync.
- Server data is never duplicated into Redux. The one intentional exception is `draftConfig`: it starts as a copy of the RTK-Query-fetched saved config (seeded once, on load) so it can be edited locally before a mutation commits it back.

## 4. Configuration model & validation

`WidgetConfig` (`types/dashboard.ts`) is the strongly-typed unit of configuration: `id`, `title`, `dataSource`, `widgetType`, `visible`, `order`, `layout`, plus optional `filter`/`sort`/`metric`/`fields`/`groupBy` (the last two: section 13). `order` is resynced to array position on every mutation (add/remove/reorder) in the slice, so it's always a reliable render order. `DashboardConfig` also carries a stable `id` (section 15) and `dashboardFilters` (section 14) alongside the widget list.

Anything that didn't just come out of the Redux store (i.e. anything read from the mock "server") is passed through `validateDashboardConfig` first, which:

- drops widgets with unknown `dataSource` values
- fills in missing `title`/`layout`/etc. from the module catalog when the `id` matches a known one
- clamps `layout.width`/`layout.height` into valid ranges
- resyncs `order` from whatever hint survived normalization
- falls back to `getDefaultConfigForRole(role)` entirely if the payload is unusable
- migrates a recognized older schema version's field names/shapes into the current ones before any of the above runs — see section 11

This is what lets the renderer assume a well-formed config always, rather than defensively checking shapes everywhere.

## 5. Widget registry & rendering pipeline

Two parallel lookup tables keep `WidgetRenderer` free of `if`/`switch` on type:

- `widgetRegistry`: `WidgetType → component` (`KpiWidget`, `BarChartWidget`, `LineChartWidget`, `TableWidget`, `ListWidget`)
- `dataSourceRegistry` (`components/dashboard/dataSources.tsx`): `DataSourceKey → component`, where each component wraps exactly one RTK Query hook (hooks can't be called dynamically/conditionally, hence one tiny wrapper per source instead of one dynamic hook call)

`WidgetRenderer` composes both: resolve data source → fetch → resolve widget component → render inside `WidgetShell`, which supplies shared loading/empty/error chrome. This is the *only* rendering pipeline in the app — both `/dashboard` and the `/configure` live preview go through it, satisfying "do not create a separate rendering implementation for the preview."

## 6. `/configure`: the drag-and-drop builder

Two-panel layout (`AvailableWidgetsPanel` + `DashboardCanvas`) under one `dnd-kit` `DndContext`:

- **Add**: dragging a palette template and dropping it on the canvas dispatches `addWidget`, which stamps a fresh `id` and inserts at the drop position.
- **Reorder**: canvas cards are also draggable (`SortableContext`); dropping dispatches `reorderWidgets` with the new id order.
- **Remove**: a widget's ✕ dispatches `removeWidget`. It only removes that dashboard's config entry — the palette is a static list (`config/widgetPalette.ts`), untouched.
- **Configure**: selecting a canvas card opens `ConfigDrawer`, a right-side drawer (kept open alongside the canvas, per the brief's preference). Its fields are context-aware: filter/sort/metric options are looked up per `dataSource` from `FILTER_OPTIONS_BY_SOURCE`/`SORT_OPTIONS_BY_SOURCE`/`METRIC_OPTIONS` in `config/dashboardConfig.ts`, so only options meaningful for that widget's data source and type are shown.
- **Live preview**: the canvas *is* the preview — every card renders through the same `WidgetRenderer` described above, fed from `draftConfig`. Changing a widget's type, filter, or layout re-renders it immediately because it's the same Redux state driving both the card and the "preview."
- **Available Widgets stays mounted independent of the canvas's loading state.** `WIDGET_PALETTE` is static, role-independent data — it never varies by role and never fetches anything — but the panel used to be nested inside the same `!draftConfig -> "Loading configuration..."` gate as the canvas, so it unmounted on every role switch along with it, for no reason tied to its own data. `DndContext` and the Available Widgets column now render unconditionally (`DndContext` has to wrap the palette regardless, since `useDraggable` requires a `DndContext` ancestor); only the canvas *column's contents* wait on `draftConfig`. Verified live with Playwright and in `ConfigurationPanel.test.tsx`: the palette's item count is unchanged both during and after a role switch.

## 7. Pagination / infinite scroll

`useInfiniteModules` owns the page cursor and exposes `modules`, `hasMore`, `loadMore`, `retry`. `getDashboardModules` (RTK Query) uses a custom `serializeQueryArgs` (keyed by role only, not role+page) and `merge` (append page 2+, replace on page 1) so all pages for a role live in one cache entry — this is what makes "don't refetch already-loaded pages" and "preserve existing modules on error" free rather than something the hook has to hand-manage. `LoadMoreSentinel` triggers `loadMore` via `IntersectionObserver`, both on scroll and when the loaded content is shorter than the viewport. A failed page keeps prior modules mounted and offers Retry, which only reissues the failed page's request.

## 8. Independent widget states & error isolation

Each widget fetches through its own `dataSourceRegistry` wrapper (its own RTK Query hook), so `WidgetShell` gives every widget an independent loading/empty/error/success state. One widget failing (including the built-in `SIMULATE_ERROR_VALUE` demo filter, in `types/dashboard.ts`) never touches its siblings — there is no shared fetch or shared error boundary across widgets.

That covered *fetch* failures, but not a *render* crash — a widget component throwing while rendering (a bad chart prop, an unexpected data shape a fetch-level check wouldn't catch) had no boundary around it at all, so React would unmount up to the nearest one, which was nothing narrower than the whole page. `WidgetErrorBoundary` (`components/dashboard/WidgetErrorBoundary.tsx`) closes that gap: `WidgetRenderer` wraps each `WidgetComponent` in one, visually matching `WidgetShell`'s existing error state (same CSS module, so no doubled card chrome) rather than a route-level Next.js error page. It resets when a `resetKey` (the widget's own config plus its data's `generatedAt`) changes, so a boundary tripped by one bad render doesn't stay permanently tripped once a config edit or a refetch gives it something new to render. Covered by `components/dashboard/WidgetErrorBoundary.test.tsx` (catches, shows the fallback, stays tripped across a re-render with the same key, resets on a new key).

## 9. Concurrent edits (optimistic concurrency)

`updateDashboardConfig` was originally last-write-wins: two saves for the same role with no ordering guarantee would silently overwrite each other, with no way to tell it had happened. Every `DashboardConfig` now carries a `revision`, an edit generation bumped by the server on every successful save (`data/mockApi.ts`). A save must include the `revision` it was loaded from; if the currently stored revision has already moved past that (someone else's save landed first), the save is rejected with `CONFIG_CONFLICT_ERROR` instead of being applied — the revision check and the store write happen with no `await` between them, so there's no window for two saves to interleave. `ConfigurationPanel` shows a banner on conflict with a **Reload Latest** action that refetches the current config and reloads the draft from it, rather than silently discarding either side's work. `Reset` was also fixed to keep the currently-loaded revision (not a hardcoded default), so resetting and then saving isn't mistaken for a conflict with yourself.

This is proven at the unit level (`data/mockApi.test.ts`): a save on the current revision succeeds and bumps it; a save on a stale revision is rejected *and* leaves the already-saved config untouched; a retried save with the fresh revision then succeeds.

**Update:** this was originally not demonstrable across two real browser tabs, because `configStore` was a plain in-memory module variable — two tabs each got their own copy. Section 15's `localStorage`-backed persistence fix (added for dashboard sharing, not for this) removed that limitation as a side effect: `updateDashboardConfig`'s revision check now reads through the same shared store both tabs write to. Verified live with two tabs sharing one browser context: Tab A hides a widget and saves cleanly; Tab B, still holding the pre-save revision, hides a different widget and saving now correctly surfaces the conflict banner instead of silently succeeding. This works *within one browser* (shared `localStorage`); it still doesn't extend to two different browsers/devices, which needs a real backend — see section 2's "backend replaces the mock API" row.

**A related, single-tab bug was found and fixed by adversarial review**: `saveDraftConfigSucceeded` originally overwrote `draftConfig` unconditionally with the mutation's response. Since nothing disabled Undo/Redo or the widget-editing controls while a save was in flight (only the Save button itself was disabled), an edit made in that ~300–700ms window was silently discarded the instant the save resolved — reproduced live with Playwright before the fix. The slice now tracks `editGeneration`, bumped on every edit to `draftConfig.widgets` (including coalesced title keystrokes and undo/redo); `handleSave` captures the role and generation at dispatch time, and `saveDraftConfigSucceeded` only adopts the response wholesale if nothing changed since — otherwise it keeps the local widgets and merges in only the server-authoritative `revision`/`updatedAt` (so the *next* save's revision check is still correct), and leaves `isDirty` true. It also refuses to apply a stale save's response if the draft has since moved to a different role. Covered by both a reducer-level test (`store/dashboardSlice.test.ts`) and a live UI-level test reproducing the exact interleaving (`ConfigurationPanel.test.tsx`).

## 10. Undo/redo (local editing history)

`draftConfig`, `isDirty`, `past`, and `future` (widget-array snapshots) all live in `dashboardSlice.ts`. Every widget-content-mutating reducer (visibility, type, data source, filter, sort, metric, layout, add, remove, reorder, and Reset) pushes the pre-change `widgets` array onto `past` and clears `future` before applying the change. `undo`/`redo` pop from one stack, push the current state onto the other, and restore. Only `widgets` is ever snapshotted — `role`/`version`/`updatedAt`/`revision` always stay at their current/latest value, which is what keeps this compatible with the optimistic-concurrency check in section 9: undoing after a save just reverts widget content locally, and a subsequent Save still checks against the correct (unchanged) revision.

A few deliberate choices:

- **Reset is itself undoable.** Given the goal — recovering from an accidental or "ruined" edit — an accidental Reset click is exactly the scenario this needs to protect against, so it pushes history like any other edit rather than clearing it.
- **A fresh load clears history, a save does not.** `loadDraftConfig` (the initial per-role fetch, and "Reload Latest" after a save conflict) and switching roles both clear `past`/`future`, since old snapshots can't reliably apply against a different role's or a different server revision's widgets. Saving, by contrast, does *not* clear history — a bad save is still locally undoable and re-saveable.
- **Consecutive edits to the same widget's title coalesce into one undo step**, tracked via `coalescingTitleWidgetId` (reset by any other action). Without this, typing a title would produce one undo step per keystroke; verified live (see below) that a full retyped title undoes in a single step, not character by character.
- **Undo/redo are also on the keyboard** (Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z), but the handler checks `document.activeElement` and does nothing while focus is in an input/textarea/select/contenteditable — otherwise it would hijack the browser's native undo inside the title field, or interfere with a `<select>`.
- **`past` is capped at `MAX_HISTORY` (50) steps**, oldest dropped first, so a long editing session can't grow history unboundedly. `future` needs no separate cap — it only grows by moving entries out of `past` via undo, so it's already bounded by the same limit.

Covered by `store/dashboardSlice.test.ts` (undo/redo, no-op when empty, branching discards stale redo on a new edit, coalescing, Reset recoverability, history clearing on load/role-switch, history surviving a save) and `components/configuration/ConfigurationPanel.test.tsx` (button enabled/disabled state through an edit → undo → redo cycle).

## 11. Schema drift (config version migration)

`validateDashboardConfig` accepts `version: number` at face value but never used to *do* anything with it — it always stamped the output as `CURRENT_CONFIG_VERSION` without checking whether the incoming shape actually matched. That's "tolerates old versions without crashing," which isn't the same as "handles old configuration versions" (brief, section 21): if an older saved config used different field names, the validator would treat those old names as *missing* and silently fall back to the module catalog's defaults (or drop the field entirely) — a user's saved customization quietly reverting with no error and no test proving that was even the actual behavior.

This codebase has only ever had one real schema, so there was no genuine prior version to migrate from. `CURRENT_CONFIG_VERSION` is now `2`, and version `1` is defined (retroactively, as a worked example — not real history) as having used `type` instead of `widgetType` and `size: {w, h}` instead of `layout: {width, height}`. `migrateConfigV1ToV2` (`lib/configValidator.ts`) runs before normalization when `raw.version === 1`, translating those old names into the current shape so the user's actual saved values survive rather than reverting to catalog defaults. It covers two different kinds of drift deliberately — a flat rename and a nested reshape — rather than just the trivial case. Only `version === 1` is recognized; anything else (missing version, an unrecognized future version) falls through to the existing best-effort normalization unchanged, by design — this is a single explicit migration step, not a general version-chain migration engine, since there's only one historical shape to migrate from today.

Proven in `lib/configValidator.test.ts`: a v1-shaped widget with a *non-default* title/layout/filter survives migration with those exact values intact (not the module catalog's defaults, which would be silently substituted if migration weren't running); a widget carrying both old and new field names prefers the current one; and versions other than `1` are confirmed to *not* trigger migration, falling back to catalog defaults for the unrecognized old field names as before.

## 12. Responsive layout

`layout.width`/`layout.height` on each widget are arbitrary (1–12 / 1–4), but `lib/layoutBuckets.ts` snaps them into a fixed set of grid-span buckets (`[3,4,6,8,12]` widths, clamped 1–4 heights) that the shared `DashboardGrid.module.css` actually implements. Responsiveness is this one grid definition reflowing at different viewport widths — there's no separate per-breakpoint layout to keep in sync, and the `/configure` canvas imports the same CSS module rather than a copy, so the builder preview matches `/dashboard` pixel-for-pixel.

## 13. Field selection & group-by

Table/List widgets had fixed columns, and Bar/Line charts were hardcoded to bucket by calendar month — both closed by adversarial review as "binding and configuration" gaps.

- **Fields**: `WidgetConfig.fields?: string[]` selects and orders which of a data source's columns a Table/List shows; unset means every column (unchanged default behavior). `TableWidget`/`ListWidget` resolve it defensively — a field that no longer exists on the data source (schema drift) is skipped, and if every selected field has drifted away, the widget falls back to showing all columns rather than an empty, broken-looking table. `FIELD_OPTIONS_BY_SOURCE` (`config/dashboardConfig.ts`) is now the single canonical column list per data source — `data/mockApi.ts` was refactored to read from it too, rather than keeping a second, driftable copy of the same column definitions.
- **Group-by**: `WidgetConfig.groupBy?: string` buckets a Bar/Line chart's series by a categorical field's value (via `lib/grouping.ts`'s `groupRowsByField`) instead of the default month-bucketing; unset keeps today's behavior. Only count-per-group is supported (not sum-per-group) — a deliberate scope cut to avoid threading a second aggregation choice through the query args for a capability nothing asked for yet. An invalid/unrecognized `groupBy` (e.g. left over after a data source's shape changed) silently falls back to month-bucketing rather than erroring, consistent with how the rest of this layer treats drift.
- **High-cardinality groups are capped visibly, not silently truncated.** `MAX_GROUPS` (8) caps how many distinct groups render as separate bars; anything beyond that is folded into one trailing "+ N more" point carrying the correct combined total — every row is still accounted for, just not as its own bar. This directly answers the brief's own "group by a field with 40,000 distinct values" scenario, and specifically avoids the silent-truncation failure mode adversarial review originally found elsewhere in this app (`TableWidget`/`ListWidget` silently slicing to 8 rows with no indicator) — since fixed the same way; see section 17.

## 14. Dashboard-level filters

Previously every filter was per-widget; there was no way to filter several widgets at once. `DashboardConfig.dashboardFilters: DashboardFilterConfig[]` adds that, with scope kept explicit rather than implicit: each entry is `{ id, dataSource, filter, appliesToWidgetIds }` — a filter only affects the widgets it's been explicitly checked into (`components/configuration/DashboardFiltersPanel.tsx`), never silently "every widget on this data source." A widget in scope has the dashboard filter override its own saved `filter` at render time (`lib/dashboardFilters.ts`'s `resolveEffectiveWidgetConfig`); its own filter is untouched in the config and takes effect again the moment it's unscoped or the dashboard filter is removed. Both `DashboardGrid` (`/dashboard`) and `CanvasWidgetCard` (`/configure`'s live preview) resolve through the same function, so — consistent with every other config-driven guarantee in this app — there's exactly one place that decides "what filter does this widget actually use," not two implementations that could drift.

Dashboard filters are covered by the same undo/redo history as widgets: `pushHistory`'s snapshot was generalized from "just `widgets`" to `{widgets, dashboardFilters}` (`store/dashboardSlice.ts`), so accidentally removing or rescoping a dashboard filter is exactly as recoverable as any other edit — the "ruined edit" guarantee wasn't left with a gap just because this capability was added later.

## 15. Dashboard identity & sharing

`DashboardConfig` now carries a real `id` (a UUID), assigned once at creation and preserved across every subsequent edit — `getDefaultConfigForRole` mints a fresh one per call, but callers that are editing an *existing* dashboard (Reset, in `ConfigurationPanel.tsx`) explicitly carry the current `id` forward, the same pattern already used to preserve `revision` across a reset. A new `/dashboard/[id]` route (`getDashboardConfigById`/`getDashboardModulesById`, mirroring the role-based endpoints) resolves a dashboard directly by that id, independent of whatever role is selected client-side, with a graceful "Dashboard not found" state (not a crash) for an id nothing has ever created. `ConfigurationPanel` surfaces the link (`/dashboard/<id>`) once a draft is loaded, with a Copy button (`navigator.clipboard`) next to it.

**Found live, not assumed — and fixed, not just documented.** The first version of this used a plain `<a href>` for the link and an in-memory `Map` for `configStore`. Verifying with Playwright surfaced two real problems: the plain anchor caused a full page reload on click, which re-executes the JS module and wipes an in-memory store — so even clicking the app's *own* link broke it. Fixed by switching to Next.js's `Link` (client-side navigation, no module re-execution) and, more fundamentally, by backing `configStore` and the role→dashboard pointer with `localStorage` instead of a `Map` (`data/mockApi.ts`'s `readStorageMap`/`writeStorageMap`, both synchronous so the optimistic-concurrency check in section 9 stays atomic). Reads go straight to `localStorage` each call rather than through an in-memory cache, so a write from one tab is visible to another without needing a `storage` event listener. Re-verified after the fix: a hard reload of the shared URL, and opening it in a genuinely separate tab within the same browser context, both correctly render the dashboard now — confirmed with two tabs sharing one Playwright browser context (the first attempt showed a false failure here because `browser.newPage()` implicitly creates an isolated context per call, not a shared one, unlike two real tabs in one window).

**What's still honestly not solved:** a different browser, profile, or device has its own `localStorage` and will never see a dashboard created in another one — "shared with another user" only holds today if that user is on the same browser/machine. Fixing that needs a real backend (see section 2's "backend replaces the mock API" row, which this identity work slots into unchanged) or, short of that, nothing client-side can fully solve it. The mechanism — stable id, dedicated route, graceful not-found, id preserved across edits, and now real same-browser persistence — is correct and tested; cross-device sharing specifically is the one piece that needs infrastructure this prototype doesn't have.

## 16. Trade-offs & deliberate scope cuts

This is a prototype, and some things were intentionally kept simple rather than "production-complete":

- **Persistence**: `localStorage`-backed (`data/mockApi.ts`'s `readStorageMap`/`writeStorageMap`), not a database — this is explicit in the brief ("do not build a real backend or database"), which also says not to make `localStorage` the *primary* source of truth; here it's the mock server's own backing store, not something the client treats as authoritative on its own, which is the distinction that brief line is actually drawing. It's still not real persistence: it's scoped to one browser/profile, so it survives reloads and works across tabs in that browser (see sections 9 and 15), but a different browser, profile, or device has its own `localStorage` and won't see any of it — that needs a real backend. The save confirmation in `ConfigurationPanel` says "Saved to this session ✓" (with a title tooltip spelling out the scope) — written before this fix, when it was more literally true; it's now slightly conservative (it survives more than "this session" implies) but still not wrong to say, since it still isn't durable in the way that copy would suggest to someone who didn't read this document.
- **No auth**: role selection is a client-side dropdown, not an authenticated session. There's no access control preventing a user from switching roles.
- **No widget-level pagination** for Table widgets — only dashboard-level module pagination (section 12–16 of the brief) is implemented; a Table widget renders all rows its data source returns (though see section 13 for how a high-cardinality *group-by* specifically is handled, which is a different code path from row rendering).
- **Filter/sort/metric/fields/group-by are fixed enumerated options per data source** (`FILTER_OPTIONS_BY_SOURCE`, `FIELD_OPTIONS_BY_SOURCE`, `GROUP_BY_OPTIONS_BY_SOURCE`, etc.), not a freeform query builder.
- **Group-by only counts rows per group, not sum-per-group** — see section 13. A deliberate scope cut, not an oversight.
- **A widget can only be in one dashboard filter's scope at a time in practice** — `resolveEffectiveWidgetConfig` (section 14) takes the first matching dashboard filter for a widget's data source; nothing in the UI currently prevents adding two dashboard filters for the same data source with overlapping scope, which would be resolved by array order rather than anything meaningful. Not reachable through normal use (the "Add Filter" flow doesn't warn about this), but worth knowing if extending this further.
- **Dashboard sharing (and now concurrency, as a side effect) work within one browser, not across devices** — see sections 9 and 15. Verified live for both, not assumed.
- **Undo/redo history is in-memory only** — it doesn't survive a page reload or a role switch (see section 10). It's capped at `MAX_HISTORY` (50) steps, oldest dropped first, so a very long editing session can't grow it unboundedly; both match the brief's own framing ("a local editing history for the current draft," not a full collaborative history system).
- **The schema-drift migration (section 11) is a worked example, not real history** — this app has only ever had one real schema. It proves the *mechanism* (a version-gated migration step preserves renamed/reshaped data instead of silently defaulting it), not an actual historical rename. It's also a single explicit step rather than a general version-chain engine, since only one prior version is defined.

## 17. Closing the last audit gaps: silent-wrongness in metrics/tables, widget crash isolation, drag-and-drop verified live

Four items were still open after section 15's work; all four are now closed.

- **KPI metrics no longer coerce bad data to 0.** `computeMetric` (`lib/metrics.ts`, renamed from `computeMetricValue`) used to read a row's value with `Number(row[valueField]) || 0` — a missing field, a renamed field (data-schema drift, distinct from the config-schema drift in section 11), or a value that drifted from numeric to text all silently became `0` and were folded into sum/average as if they were a real, valid zero. `sum`/`average`/`latest` now return `{ value, invalidCount }`: rows that can't be read as a finite number are excluded from the computation (not counted as zero), and `average` divides by the count of *valid* rows, not every row, so excluding bad data changes the denominator correctly rather than just zeroing the numerator. `KpiWidget` renders a visible `role="alert"` warning whenever `invalidCount > 0`, naming exactly how many rows were excluded and that the true value may be higher — the KPI number itself is now either fully trustworthy or visibly flagged, never silently wrong. Covered by `lib/metrics.test.ts` (sum/average exclude and count invalid rows correctly, average's denominator, `latest` flagging an invalid picked row, `count` unaffected).
- **Table/List row truncation is now visible, not silent.** Both widgets always rendered at most 8 rows (`data.rows.slice(0, 8)`) with nothing indicating more existed — a widget could be quietly showing 8 of 4,000 rows. `MAX_VISIBLE_ROWS` (`lib/format.ts`) is now the single named constant both widgets slice against, and each shows a footer notice ("Showing 8 of N rows/items · M more not shown") whenever `data.rows.length` exceeds it. This is the same principle already applied to chart group-by capping in section 13, now applied consistently to the two widget types that hadn't gotten it yet. Covered by `components/widgets/TableWidget.test.tsx` and the new `components/widgets/ListWidget.test.tsx` (no notice when everything fits, exact counts in the notice when it doesn't).
- **A widget render crash no longer takes down the page.** See section 8's update — `WidgetErrorBoundary` scopes a render-time failure to the one widget.

## 18. A filter/sort change could briefly show the *old* filter's data under the *new* filter's label

Reported by the user testing the app directly ("clicking Successful on Payments doesn't show only successful, need to click Payments again to get it to update") — reproduced live, root-caused, fixed, and given regression coverage, not just patched from the symptom description.

**What was actually happening.** `WidgetRenderer` computes both the widget's header caption (`meta`, from `config.filter?.label`) and its RTK Query args (`{ filter: config.filter, sort: config.sort, groupBy: config.groupBy }`) from the same `config` prop in the same render, so those two can never disagree — the bug wasn't there. It was in how the result was trusted: `state` was computed from `isLoading` alone (`isLoading ? "loading" : ...`), and `isLoading` is only `true` for a query's very first-ever fetch. When `config.filter` changes to a combination this widget hasn't fetched before, RTK Query's hook keeps returning the *previous* args' cached `data` (with `isFetching: true`, `isLoading: false`) while the new request is in flight — a deliberate RTK Query behavior that avoids flicker on a plain revalidation. But the header had already moved on to the new filter's label in that same render, so for the ~350–900ms the mock API's simulated latency (`data/mockApi.ts`'s `delay()`) takes to resolve, the widget showed the *old* filter's rows underneath the *new* filter's caption, with no loading indicator distinguishing that from a settled, correct state.

**Why it was hard to spot casually.** Most filter/sort combinations reachable from the default catalog dashboard happen to already be cached by *some* widget on the canvas (e.g. the built-in "Successful Payments" and "Failed Payments" widgets pre-warm those exact combinations), so switching to them via the config drawer looks instant. The bug only became externally visible on a combination nothing had fetched yet — which is exactly what happens when a *dashboard-level* filter (section 14) is scoped to a widget that doesn't already carry a matching filter/sort pairing of its own. Confirmed live with fine-grained polling (30ms intervals) and by instrumenting the RTK Query hook's own `isFetching`/`data` values directly: the mismatched window was real, reproducible, and bounded by the mock's latency window, not a one-off timing fluke.

**The fix.** `state` now also checks `isFetching`, not just `isLoading`: `isLoading || isFetching ? "loading" : ...` (`components/dashboard/WidgetRenderer.tsx`). Any refetch — whether it's the widget's first-ever load or a later args change — now shows the existing loading skeleton until the response for the *current* args actually lands, so a widget's displayed data can never be observed out of step with the configuration its own caption claims to be showing. This is the same "either fully correct or visibly not yet correct, never silently wrong" standard already applied to metrics and row truncation in section 17.

Covered by a new test in `components/dashboard/WidgetRenderer.test.tsx` that changes a rendered widget's filter to a combination the test's store has never fetched and asserts that at the instant right after the change — before any `await` — the widget is either showing a loading state or already-correct data, never a mix of the two. Verified this test actually catches the regression (temporarily reverted the fix, confirmed the test fails with the exact stale value the bug produces, restored the fix, confirmed it passes) rather than assuming it does.

## 19. What would change with more time

- Swap `fakeBaseQuery` for `fetchBaseQuery` against a real API (the seam described in section 2 is designed for exactly this) — this is what would let the concurrency check in section 9 *and* dashboard sharing in section 15 work across two real users on different devices/browsers, which is the one thing the `localStorage` fix (already done) can't reach.
- Add a `storage` event listener so two tabs open on the *same* dashboard update live without either needing to navigate/refetch — today a write from one tab is only picked up by another on its next read (a role switch, a manual reload, an existing invalidation), not instantly while both sit idle.
- Let a dashboard filter's scope resolution order be explicit (or prevent overlapping scope in the "Add Filter" UI) rather than implicitly first-match, if a widget being scoped into two same-data-source dashboard filters ever becomes a real workflow (see section 16).
- Support sum-per-group (not just count-per-group) for group-by charts, and expose real Table/List row pagination (today `MAX_VISIBLE_ROWS` is a visible cap, not paging — see section 17) as its own, separate capability from the group-by cap in section 13.
- Add real authentication and make role a property of the authenticated user rather than a free dropdown.
- Fix the dev-only `dnd-kit` hydration-mismatch console warning noted in section 17 (a stable, SSR-safe id source instead of `dnd-kit`'s default per-render counter) — cosmetic today, but worth silencing so real hydration issues don't get lost in the noise.
- Section 18's fix (`isLoading || isFetching`) shows the loading skeleton on *every* refetch, including ones where the data turns out unchanged — a reasonable, correctness-first default given this app's "never show stale/mismatched data" standard, but a busier real deployment might want a subtler "refreshing" indicator (e.g. a small spinner overlay on the existing content) instead of the full skeleton specifically for same-widget revalidations, reserving the full skeleton for genuine filter/sort/groupBy changes.
